1. DESCRIPTION DU PROJET
---------------------------------------------------
Plateforme unique regroupant trois volets :
- Visioconference (type Microsoft Teams, en mieux)
- Plateforme de formation en ligne avec cours et certifications
- Boutique e-commerce vendant des cours ET des produits independants,
  accessible aussi aux visiteurs qui ne suivent pas de cours (achat invite)

Localisation du porteur de projet : Dakar, Senegal.
Aucune option payante souhaitee, sauf pour l'hebergement.
Le porteur n'est a l'aise ni avec Linux ni avec Docker.


2. STACK TECHNIQUE VALIDEE
---------------------------------------------------
Backend            : Laravel (PHP)
Hebergement backend : Laravel Cloud (managed, pas de serveur a gerer)
Base de donnees     : PostgreSQL (via Laravel Cloud)
Visioconference (SFU) : LiveKit Cloud (pas d'auto-hebergement de coturn)
Videos de cours (VOD) : Bunny Stream ou Cloudflare Stream (liens signes,
                        transcodage adaptatif — ne jamais stocker de video
                        brute sur Laravel Cloud, trop cher en bande passante)
Stockage fichiers statiques : Cloudflare R2 (PDF certificats, images —
                              egress gratuit)
Paiement local      : CinetPay ou PayDunya (Wave, Orange Money — adapte
                      au marche senegalais/UEMOA)
Paiement international (optionnel) : Stripe
Emails transactionnels : Resend ou Postmark

Raison des choix : eviter Docker et l'administration Linux (ports UDP,
TURN/coturn), tout en gardant un cout d'exploitation maitrise
(15-40 EUR/mois estime au demarrage).


3. MODELE DE DONNEES VALIDE (ERD)
---------------------------------------------------
Entites principales et relations cles :

- USERS : comptes utilisateurs (id, name, email, password)

- ORDERS : commandes
  - user_id NULLABLE (permet l'achat invite)
  - guest_email, guest_name (pour les invites)
  - status (pending | paid | failed)
  - total

- ORDER_ITEMS : lignes de commande POLYMORPHIQUES
  - itemable_type / itemable_id (morphTo en Laravel)
  - pointe vers COURSES ou PRODUCTS
  - permet un panier mixte (cours + produit dans la meme commande)

- COURSES : cours (id, title, slug, price, stream_video_id)

- PRODUCTS : produits independants (id, name, slug, price, stock)

- ENROLLMENTS : inscription d'un utilisateur a un cours
  - creee automatiquement apres paiement reussi
  - (id, user_id, course_id, progress, completed_at)

- CERTIFICATES : certificat lie a une inscription terminee
  - (id, enrollment_id, file_path -> stocke sur R2)

Point cle : la relation polymorphique sur ORDER_ITEMS est ce qui permet
de vendre des cours ET des produits sans dupliquer la logique de commande,
et le guest_email sur ORDERS permet l'achat sans compte.

FIN DU RESUME
=====================================================
Voici comment ton projet Laravel est organisé, du clic de l'utilisateur jusqu'à la base de données :## Comment lire ce schéma avec tes fichiers concrets

**1. Routes** — `routes/web.php` gère les pages du site (storefront + admin), `routes/api.php` gère les endpoints JSON (utile pour un futur webhook CinetPay, ou une appli mobile). `routes/console.php` c'est pour les commandes Artisan personnalisées, pas pour le web.

**2. Contrôleurs** — trois dossiers avec un rôle distinct :
- `Http/Controllers/Storefront/` → ce que voit le client : `CatalogController` (liste produits/cours), `CartController` (panier), `CheckoutController` (validation commande + déclenchement paiement CinetPay)
- `Http/Controllers/Admin/` → back-office : `ProductController`, `CourseController` pour gérer le catalogue
- `Http/Controllers/Api/` → **vide pour l'instant**. C'est ici que tu mettras par exemple le webhook qui reçoit la confirmation de paiement de CinetPay (CinetPay appelle ton serveur en POST après un paiement)

**3. Modèles Eloquent** — ils représentent tes tables et leurs relations :
- `Order` ↔ `OrderItem` ↔ `Product` : une commande contient plusieurs lignes, chaque ligne pointe vers un produit
- `Enrollment` relie `User` à `Course` (une inscription à un cours)
- `Certificate` est généré après complétion d'un `Enrollment`
- `Enums/OrderStatus.php` définit les états possibles d'une commande (pending, paid, failed, etc.) — c'est ce qui pilote toute la logique métier autour du paiement

**4. Services métier** — la logique qui ne doit pas être dans les contrôleurs :
- `CinetPayService.php` → initialise un paiement, vérifie une transaction, traite les webhooks
- `LiveKitService.php` → génère les tokens/salles pour la diffusion vidéo des cours
- `CertificateService.php` → génère le PDF du certificat une fois le cours terminé

**5. Base de données** — tu es en SQLite (`database/database.sqlite`), simple pour développer, à migrer vers MySQL/PostgreSQL en production si besoin.

**Dossiers vides à noter** : `Notifications/` (emails de confirmation de commande, d'inscription...) et `Policies/` (règles d'autorisation, ex: "seul l'admin peut modifier un produit") — normal qu'ils soient vides à ce stade du squelette, ils viendront avec la logique métier.

**Ce qui manque encore visiblement** : `resources/views/` est vide → aucune page HTML/Blade n'existe encore, c'est pour ça que localhost affichait une erreur de connexion en plus du serveur non lancé.

Maintenant qu'on a la vue d'ensemble, veux-tu qu'on commence par corriger la base technique (`.env`, migrations) ou plutôt regarder le contenu actuel de `CinetPayService.php` pour voir ce qui est déjà fait ?
